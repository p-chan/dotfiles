# 良いコメント

## 目的

コメントは、コードだけでは十分に伝わらないコンテキストを、将来そのコードを読む人に伝えるために書きます。

主な読者は、そのコンテキストを知らない将来の開発者です。

## 基本原則

- コメントを書く前に、「What」を命名やコード構造で表現できないかを考えます
- コメントには、コードで十分に表現できない「Why / Why not」を書きます
- 必要に応じて、意図、背景、制約、前提、トレードオフ、例外など、コードだけでは十分に伝わらないコンテキストを補います
- コメントは、その場限りの会話や作業セッションを知らなくても理解できるように書きます
- 簡潔かつ正確に書き、コードと重複・矛盾しないようにします

## 情報の責務

- 新たな情報を書くときは、その情報に最も適した記録場所を考えます
- コメントは、コードの理解に必要なコンテキストを保持します
- それ以外の情報は、必要に応じてコミットメッセージ、Issue、Pull Request、ADR、仕様書などの適切な記録場所に記録し、コメントから参照します
- その種類の情報に適した記録場所がプロジェクトに用意されていない場合は、多少長くなっても、必要なコンテキストをコメントに書きます
- 将来の改善や修正を示す必要がある場合は、TODO・FIXME の利用を検討します
- TODO・FIXME には、理由や解消条件を添えます
- TODO・FIXME が長くなる場合や、継続的な管理が必要な場合は、Issue 化し、コメントから参照することも検討します

## 例外

命名やコード構造だけでは処理内容を十分に表現できず、構造化や抽象化も過剰になる場合は、「What」を補足しても構いません。

例えば、GitHub Actions 内の局所的で複雑なシェル処理などが該当します。ただし、まずはジョブやステップの name、処理の分割、Composite Action、スクリプトの外出しなどで表現できないかを考えます。
