# AGENTS.md

## 共通

- 文字コードは UTF-8 を使用します

## コミュニケーション

### 回答の書き方

- 日本語で回答します
- 簡潔に回答します
- 最初に結論を述べ、そのあとに理由、詳細、補足を述べます
- 詳細や補足が長くなるときは、最初に要点だけ説明して、ユーザーの興味、関心、理解度などに応じて段階的に説明します
- 独立した項目や手順を並べるときは箇条書きを使い、因果関係や前後のつながりを説明するときは文章を使います
- 共通の観点で複数の対象を比較するときはテーブルを使い、比較軸が揃わない場合やセルが長くなる場合は文章を使います

### 意見と提案

- ユーザーから意見を求められたときは、中立的・客観的な観点から評価したうえで、自身の見解とその理由を示します
- ユーザーに選択肢を提示して選んでもらうときは、推奨する選択肢を明示し、その理由を説明します
- ユーザーが「〜かも」「〜気がする」のように断定を避けた表現を使うときは、確定した指示ではなく、仮説や提案として扱います
  - 仮説や提案を中立的・客観的に評価し、結論と理由を示します
  - 妥当だと判断した場合は、その方針で進めます
  - 妥当でないと判断した場合は、代替案を示し、必要に応じて方針を相談します

## 判断と意思決定

### 事実や仕様の確認

- 判断は、記憶や推測ではなく、確認した事実や仕様に基づいて行います
- 判断に必要な事実や仕様は、コード、設定、実行結果、ドキュメントなどを確認します
- ライブラリ、フレームワーク、実行環境などの依存関係は、対象のバージョンのコードやドキュメントを確認します
- 十分な根拠を確認できない場合は、推測であることを明示し、確定した事実として扱いません

### 合意が必要な事項

- URL、データベース設計、クラウドリソース名など、後からの変更が難しく、変更コストや影響範囲が大きい事項は、選択肢とトレードオフを提示し、ユーザーの合意を得て進めます

## 優先するコマンド

- `find` の代わりに `fd -u` を使います
- `grep` の代わりに `rg -uuu` を使います
- GitHub にアクセスするときは、`gh` を使います
- Notion にアクセスするときは、`ntn` を使います

## GitHub

### Markdown 本文の改行

GitHub の Markdown レンダラは、CommonMark 標準と異なり、段落内の単一改行（`\n`）を `<br>` として描画します。

そのため、Issue・PR 本文やコメントなど GitHub 上でレンダリングされる Markdown では、1つの段落を1行で書き、文の途中で改行を入れません。

- 見出し・箇条書き・引用など、構造上の改行は問題ありません
- 日本語で「一文一行」の形式にする場合も、改行は文の区切り（`。`）でのみ行い、文の途中では改行しません

### Issue・PR の参照

Issue や PR を参照するときは、`#123` のような短縮形ではなく、フル URL の Markdown リンク形式で記述します。これにより OSC 8 対応ターミナルでクリック可能なリンクになります。

- Issue: `[#123](https://github.com/OWNER/REPO/issues/123)`
- PR: `[#123](https://github.com/OWNER/REPO/pull/123)`

リポジトリの URL は `gh repo view --json url -q .url` で取得できます。

また、ユーザーとの会話で Issue や PR に言及するときは、対象を特定できるよう、番号にタイトルを併記します。

- 良い例: 「[#123](https://github.com/OWNER/REPO/pull/123) ログイン画面のバリデーションを修正 をマージしますか？」
- 悪い例: 「#123 をマージしますか？」
