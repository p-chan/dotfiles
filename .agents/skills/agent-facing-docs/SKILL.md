# エージェント向け文書

エージェント向け文書は、エージェントが必要な情報を、必要なときに、必要なだけ、確実に得られるように設計する。

Skill を扱う場合は、固有のルールについて `references/skills.md` を読む。

## 情報の配置

情報は、役割や必要になる条件に応じて配置する。

機械的に検証・強制できることは、文書ではなく、リントやテスト、スクリプトなどの仕組みで担保する。

文書として扱う情報は、次のように配置する。

- 継続的に適用する指示 → 指示ファイル
- 特定の作業・技術・領域で必要になる知識や手順 → Skill
- プロジェクトの SSoT として保持する背景・設計・仕様など → `docs/` などの参照文書

継続的に適用される指示ファイルには、その適用範囲で広く必要になる非自明な指示を書く。

配置先は、適用範囲に応じて決める。

- すべてのプロジェクトに適用 → ユーザー共通の指示ファイル
- プロジェクト全体に適用 → プロジェクト共通の指示ファイル
- 特定の範囲に適用 → その範囲に近い指示ファイル

Skill と参照文書は、役割と想定読者に応じて使い分ける。

| | Skill | 参照文書 |
| --- | --- | --- |
| 役割 | 特定の作業・技術・領域で必要な知識や手順を、必要なときに読み込ませる | プロジェクトの知識を SSoT として保持する |
| 想定読者 | エージェント | 人間とエージェント |

指示ファイルや Skill から共通して参照するプロジェクトの知識は、参照文書を SSoT とする。

Skill の内部でだけ必要になる情報は、その Skill の参照ファイルに置く。

## 情報源を一つにする

同じ情報は複数箇所に持たず、SSoT に集約する。

コード、設定、ディレクトリ構成、コマンドの `--help` などから容易に取得・理解できる情報は、それらを SSoT とする。

情報源から容易に取得・理解できる情報を文書へ複製すると、その文書は陳腐化しうるキャッシュになる。

一方で、参照頻度が高かったり、調査や取得にコストがかかる情報は、文書へ要約・キャッシュすることを検討する。

文書には、次のようなコードや設定などから容易に分からない情報を優先して書く。

- 暗黙の規約
- 判断理由
- 非自明な制約
- 繰り返しハマりやすい落とし穴

## 情報を段階的に開示する

その文書を読むときに常に必要な情報は、その文書に置く。

一部の場面でだけ必要な情報は別文書へ分離し、参照先と**いつ読むか**をセットで書く。

悪い例:

```md
詳しくは `docs/database-migrations.md` を参照する。
```

良い例:

```md
DB スキーマを変更するときは `docs/database-migrations.md` を参照する。
```

その文書を読むときに常に必要な情報でも、文書が長くなり重要な手順や指示が埋もれる場合は、意味のまとまりや実行経路に沿って分離を検討する。

単にファイルを短くすることだけを目的に分離しない。

## 関連する情報を近くに置く

同じ概念に関する定義、ルール、例外、注意事項は近くにまとめる。

一つの概念を複数の文書やセクションへ散らさず、必要な情報をまとめて確認できるようにする。

## 指示の書き方

指示は、禁止したい行動を否定形で書かず、取るべき行動を肯定形で書く。

悪い例:

```md
不要なコメントを書かない。
```

良い例:

```md
コメントはコードから分からない理由を説明するときに書く。
```

禁止が必要な場合は、禁止する行動と代わりに取るべき行動をセットで示す。

```md
生成されたファイルは直接編集せず、生成元を編集して再生成する。
```

指示は、日常的に利用するモデルの挙動に意味のある差を生むものに絞る。

## 手順と完了条件

手順は実行順に並べ、各手順に完了したか判断できる条件を持たせる。

完了条件に求める成果や根拠を明確にすることで、必要なレグワークを引き出し、完了条件から導けない手順だけ書く。

悪い例:

```md
1. ログを確認する。
2. 関連するコードを調査する。
3. 障害の原因を調査する。
```

良い例:

```md
障害の原因を特定し、その根拠を示す。
```

## 文書を整理する

文書の編集は、足し算だけでなく、引き算も考える。

文書を編集するときは、追加する内容だけでなく、既存の内容も見直す。

意図する挙動を保てる範囲で、不要になった内容は削除し、変更すべき内容は更新し、新しい内容が必要な場合は追加する。
